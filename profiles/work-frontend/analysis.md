# 读者与工作目标
读者是前端开发者。本类只服务页面与组件实现、设计稿转可访问页面、自动化测试、浏览器调试、代码审查和重构，核心是工作如何用 AI，不是追新闻。
典型实践链：页面需求、设计稿或最小复现代码 → AI辅助实现或定位问题 → 可运行组件、测试或修复 → 构建、交互、可访问性和回归验证。

# 评分（0—10）
9—10：材料给出明确工作任务、输入与输出、可复现操作、适用条件及验证方法；原文或官方文档可以核对，读者可开始一个小任务。
7—8：官方文档、可信教程或案例明确给出本类真实工作用途和至少一个可开始的动作，有依据形成可复用路径，即使尚未实机验证或原文未列全输入输出、步骤、条件、验收，也可达此档；未验证部分须标注。完整字段与独立效果验证是9—10档的加分证据，不是7分硬性前置。
4—6：泛泛工具介绍、只有效果宣称、缺少具体工作用途和可开始动作，或关键依据仅为不可核验的片段；单纯发布、融资、benchmark与排行榜最高4分，即使热度很高。
0—3：无 AI 关系、与本类工作无关、广告、夸张赚钱/省时承诺、无依据的观点或重复资讯。
不得因当天缺稿提高分数。7分门槛，不凑数；每类每日最多一条由最终配额执行。
没有亲自运行证据不得写“已实测”；厂商演示、自述与独立验证分开。涉及真实用户数据须指出脱敏与授权条件；付费、登录、部署、版本限制写清。Star数和讨论热度不代替工作价值。输出具体任务标签。

# 筛选阶段的证据边界
当前输入可能是长文的开头、中段和结尾节选；只依据所给证据评分，不把未展示的章节断言为不存在。筛选考察是否有具体工作任务、可用方法与可验证交付物的依据；不要求一篇材料同时覆盖本类所有任务。仅因节选没有完整命令、全部3—5步或独立实测，不应否定已明确展示的工作方法；操作和当前条件由后续enrichment核对，不得在分析时补造。只有标题或搜索片段、正文读取失败、仅泛泛功能宣称时，仍需降分并说明具体缺口。
reason用简体中文简要写明“任务/证据/缺口”，指出实际看到了什么与为何未达7分；不要只写不相关或资料不足。保持平台JSON输出契约，score是0—10数字，reason、summary是字符串，tags为字符串数组。
